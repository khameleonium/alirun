> **Для кого это руководство:**  
> Этот справочник написан простым, понятным языком как для тех, кто впервые знакомится с администрированием Linux, так и для опытных разработчиков, желающих разложить всё по полочкам. ## 1. Фундаментальные основы: процессы, демоны и init

### Что такое процесс и демон

- **Процесс (Process)** — это любая запущенная в системе программа (текстовый редактор, скрипт на Python, браузер). У каждого процесса в Linux есть свой уникальный идентификатор — **PID** (Process ID).
- **Обычная программа** запускается пользователем в терминале и «держится» за него: если вы закроете окно терминала, процессу будет отправлен сигнал `SIGHUP` (терминал закрылся), и программа завершится.
- **Демон (Daemon)** — это фоновый процесс, который работает автономно:
  1. Он отвязан от управляющего терминала (не зависит от того, открыт терминал или нет).
  2. Он работает в фоне и часто запускается автоматически при старте операционной системы или входе пользователя.
  3. Традиционно имена системных демонов в Linux заканчиваются на букву «d»: `sshd` (SSH-демон), `systemd`, `crond`, `dockerd`.

### Зачем нужна система инициализации (Init, PID 1)

Когда компьютер включается, ядро Linux инициализирует железо и запускает **самую первую программу в системе**.
У этой программы всегда идентификатор **`PID 1`**. Это и есть **Система Инициализации (Init System)**.

**Задачи PID 1:**
1. **Запуск дерева процессов:** Поднять сеть, файловые системы, графическую оболочку, службы баз данных.
2. **Мониторинг:** Если фоновый сервис аварийно упал (Segmentation fault / ошибка в коде), именно система инициализации замечает его смерть и, если это предусмотрено настройками службы (в systemd — параметр `Restart=`), автоматически перезапускает. Классический SysVinit сам службы не перезапускает (исключение — строки `respawn` в `/etc/inittab`).
3. **«Усыновление» процессов-сирот:** Когда родительский процесс погибает, его дочерние процессы («сироты») передаются на попечение PID 1 (или ближайшего назначенного «сборщика» — subreaper, например `systemd --user`). Когда сирота сам завершится, PID 1 заберёт его код завершения, и процесс не останется в таблице процессов «зомби».
4. **Упорядочивание зависимостей:** База данных не должна стартовать, пока не поднялась сеть и не смонтирован диск.

В подавляющем большинстве современных дистрибутивов (Ubuntu, Debian, Fedora, Arch, Manjaro, Linux Mint, RHEL) в роли PID 1 выступает **systemd**. В специализированных или минималистичных дистрибутивах (Alpine, Gentoo, Devuan) используются **OpenRC** или **SysVinit**.

### Системный уровень (System) против Пользовательского (User)

В Linux управление службами чётко разделено на две зоны ответственности:

| Параметр | Системный уровень (System Scope) | Пользовательский уровень (User Scope) |
| :--- | :--- | :--- |
| **Для кого работает** | Для всего сервера/ПК в целом | Только для конкретного вошедшего пользователя |
| **Кто управляет** | Администратор (`root`, через `sudo`) | Обычный пользователь (без `sudo`) |
| **Когда запускается** | При включении питания компьютера | В момент входа пользователя в систему (login) или при загрузке, если включён linger (см. раздел 2) |
| **Типичные примеры** | Веб-сервер Nginx, СУБД PostgreSQL, служба SSH, Docker | Telegram, синхронизация Syncthing, пользовательские боты, агент уведомлений |
| **Команда systemd** | `systemctl <действие> <служба>` | `systemctl --user <действие> <служба>` |

> **Правило безопасности:** Если вы пишете своего Telegram-бота, фоновый скрипт или парсер для личных нужд, **никогда не запускайте его с правами root в системном профиле**. Запускайте его в **пользовательском профиле (`--user`)** — для этого не нужны права администратора, и такой сервис не сможет повредить системные файлы.

### Сетевая активность: Слушающие порты (LISTEN) vs Исходящие сессии (ESTABLISHED)

Частый источник путаницы: *«Почему для веб-сервера пишется порт `:80`, а для Telegram или браузера сетевой порт не отображается?»*

```
СЕРВЕР (LISTEN):
  [Клиент из интернета] ──── подключение ───> [Порт 80 на вашем ПК] (Ждёт входящих)

КЛИЕНТ (ESTABLISHED):
  [Telegram на вашем ПК] ─── исходящий запрос ──> [Сервер Telegram 149.154.167.50:443]
```

1. **Слушающий сокет (`LISTEN`):**
   - Служба резервирует порт и «слушает» входящие запросы извне.
   - Это серверные демоны: Nginx (`:80`), SSH (`:22`), Syncthing (`:8384`).
   - К слушающему порту может подключиться любой, кто до него «достаёт» по сети: это зависит от адреса привязки (`0.0.0.0` / `::` — со всех сетевых интерфейсов, `127.0.0.1` — только с этого же компьютера) и правил фаервола. Проверка прав (логин, токен) — уже забота самого приложения.
2. **Исходящее установленное соединение (`ESTABLISHED`):**
   - Клиентская программа (Telegram, Discord, браузер) **не слушает порт**.
   - Она сама открывает исходящее соединение к удалённому серверу (например, к `149.154.167.50:443`).
   - Ядро Linux для этого соединения выделяет временный локальный порт (эфеме́рный, например `54321`), но входящие подключения извне на него не принимаются.

## 2. Systemd: Современный стандарт Linux

### Архитектура и типы юнитов

В systemd всё описывается конфигурационными файлами, которые называются **юнитами (Units)**. Тип юнита определяется его расширением:

- **`.service`** — описывает службу/демон (как запускать программу, как перезапускать при сбое).
- **`.timer`** — таймер планировщика (аналог cron, запускает одноимённый `.service` по расписанию).
- **`.target`** — логическая группа юнитов (например, `graphical.target` объединяет всё необходимое для запуска графического стола).
- **`.socket`** — активация службы по сокету (сетевому или локальному Unix-сокету): systemd сам держит сокет открытым и запускает сервис только при первом подключении.
- **`.slice`** — распределение системных ресурсов (ограничение CPU и RAM через Linux cgroups).

---

### Иерархия каталогов и приоритеты (Vendor, Generator, Admin)

systemd считывает юниты из строго определённых каталогов. Если файл с одним и тем же именем есть в нескольких каталогах, используется тот, что выше в списке.

**Системный уровень** (`systemctl`), от высшего приоритета к низшему:

```
Высший приоритет
│ /etc/systemd/system.control/     ┐ служебные каталоги: systemctl set-property,
│ /run/systemd/transient/          │ временные юниты systemd-run,
│ /run/systemd/generator.early/    ┘ ранние генераторы
│ /etc/systemd/system/             ← ВАШИ файлы (администратор)
│ /run/systemd/system/             runtime-юниты (живут до перезагрузки)
│ /run/systemd/generator/          обычные генераторы
│ /usr/local/lib/systemd/system/   локально установленный софт
│ /usr/lib/systemd/system/         ← пакеты дистрибутива (vendor)
│ /run/systemd/generator.late/     поздние генераторы
▼
Низший приоритет
```

**Пользовательский уровень** (`systemctl --user`), сокращённо:

```
Высший приоритет
│ ~/.config/systemd/user.control/, /run/user/<UID>/systemd/transient/,
│ /run/user/<UID>/systemd/generator.early/          служебные каталоги
│ ~/.config/systemd/user/          ← ВАШИ файлы
│ /etc/systemd/user/               администратор — для всех пользователей
│ /run/user/<UID>/systemd/user/    runtime-юниты
│ /run/user/<UID>/systemd/generator/                обычные генераторы
│ ~/.local/share/systemd/user/     юниты, установленные в домашний каталог
│ /usr/lib/systemd/user/           ← пакеты дистрибутива (vendor)
│ /run/user/<UID>/systemd/generator.late/           поздние генераторы (сюда попадают юниты XDG-автозапуска)
▼
Низший приоритет
```

> Точный список каталогов для вашей системы покажут команды `systemd-analyze unit-paths` и `systemd-analyze --user unit-paths`. Каталог `/lib/systemd/system/` в современных дистрибутивах — это просто ссылка на `/usr/lib/systemd/system/`.

#### Почему нельзя редактировать файлы в `/run/` и `/usr/lib/`:
1. **Каталог `/run/`** расположен на файловой системе `tmpfs` прямо в оперативной памяти: всё, что там лежит, исчезает при перезагрузке. Кроме того, каталоги генераторов (`/run/systemd/generator*`, `/run/user/<UID>/systemd/generator*`) заполняются заново при каждом `systemctl daemon-reload` — ручные правки там будут **безвозвратно стёрты** уже при следующей перезагрузке конфигурации.
2. **Каталог `/usr/lib/systemd/`** принадлежит пакетному менеджеру системы (`apt`, `dnf`, `pacman`). При очередном обновлении пакета ваш файл будет перезаписан исходной версией от разработчиков.

#### Куда сохранять свои настройки:
- **Для обычного пользователя:** всегда в `~/.config/systemd/user/`
- **Для системных служб (root):** всегда в `/etc/systemd/system/`

### Механизм переопределений (Override / Drop-in)

Что делать, если в системе уже есть служба (например, `/usr/lib/systemd/system/docker.service`), но вы хотите изменить в ней всего одну строчку (например, добавить флаг запуска или переменную окружения)?

Есть два способа:

#### Способ 1: Точечный оверрайд (Drop-in snippet) — Рекомендуемый способ
Вы не копируете весь файл целиком, а создаёте специальную папку `<имя_службы>.service.d/` и кладёте туда файл `override.conf`, в котором описываете **только то, что меняется**.

Пример для системной службы `docker`:
Файл: `/etc/systemd/system/docker.service.d/override.conf`
```ini
[Service]
# Очищаем старую команду ExecStart (обязательно для изменения ExecStart!)
ExecStart=
# Задаём новую команду
ExecStart=/usr/bin/dockerd -H fd:// --bip=192.168.100.1/24
```
Всё остальное содержимое исходного юнита останется нетронутым и продолжит автоматически обновляться вместе с системой!

Проще всего создать такой файл командой `sudo systemctl edit docker` (для пользовательских служб — `systemctl --user edit <имя>`): она сама создаст каталог и `override.conf`, откроет редактор и после сохранения выполнит `daemon-reload`.

#### Способ 2: Полное замещение (Full Override)
Вы копируете файл целиком в `/etc/systemd/system/<имя>.service` (или `~/.config/systemd/user/<имя>.service`). Файл с таким же именем из каталога с более высоким приоритетом полностью замещает исходный файл (не путать с `systemctl mask` — это другая операция, см. шпаргалку ниже). Минус способа: обновления пакета для этого юнита больше не применяются, пока вы не удалите свою копию.

> **ВАЖНО:** После любого ручного создания или изменения unit-файлов на диске вы **обязаны** выполнить (команда `systemctl edit` делает это сама):
> - Для системных служб: `sudo systemctl daemon-reload`
> - Для пользовательских служб: `systemctl --user daemon-reload`
> 
> Без этой команды systemd продолжит использовать старую версию юнита, загруженную в память.

### Анатомия `.service` файла (построчный разбор всех секций)

Любой `.service` файл представляет собой текстовый файл в формате INI и состоит из трёх базовых секций. Пример системной службы (файл `/etc/systemd/system/my-web.service`):

```ini
[Unit]
Description=Мой веб-сервис на Python
Documentation=https://example.com/docs
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=virusfun
Group=virusfun
WorkingDirectory=/home/virusfun/my-web-app
ExecStart=/usr/bin/python3 /home/virusfun/my-web-app/server.py --port 8080
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
Environment="APP_ENV=production" "PORT=8080"
EnvironmentFile=-/home/virusfun/my-web-app/.env

# Ограничения безопасности и ресурсов (cgroups)
MemoryMax=512M
CPUQuota=100%

[Install]
WantedBy=multi-user.target
```

#### Разбор параметров секции `[Unit]` (Метаданные и зависимости)
- `Description=` — Человекочитаемое описание службы. Отображается в `systemctl status` и утилите `alirun`.
- `After=` — Определяет **порядок запуска**: служба стартует *после* указанных юнитов. В примере: стартовать только после того, как сеть полностью поднялась (`network-online.target`). Это работает только в системных службах: в пользовательском менеджере (`--user`) цели `network-online.target` не существует.
- `Wants=` — **Мягкая зависимость**: при запуске нашей службы systemd запустит и указанный юнит (без `After=` — параллельно), но если тот не стартует или упадёт, наша служба всё равно запустится и продолжит работу.
- `Requires=` — **Жёсткая зависимость**: указанный юнит запускается вместе с нашим. Если он не смог стартовать (и на него задан `After=`), наша служба тоже не запустится. Если его явно остановить или перезапустить (`systemctl stop/restart`), наша служба остановится или перезапустится вместе с ним. Но если зависимость позже **сама упадёт**, `Requires=` нашу службу не остановит — для такого поведения используется `BindsTo=`.

#### Разбор параметров секции `[Service]` (Параметры запуска и жизненный цикл)
- `Type=` — Механизм запуска программы (подробнее разбирается ниже). `simple` — стандарт.
- `User=` и `Group=` — Имя пользователя и группы, от которых будет работать процесс. (Используется только в системных службах; в пользовательских службах `--user` эти параметры не указывают — процесс всегда работает от имени владельца пользовательского менеджера.)
- `WorkingDirectory=` — Рабочая папка (всё равно что выполнить `cd /каталог` перед стартом).
- `ExecStart=` — **Главная команда запуска**. Лучше всегда указывать **абсолютный путь** к исполняемому файлу (`/usr/bin/python3`). Начиная с systemd 239 допускается и просто имя (`python3`), но тогда оно ищется в фиксированном списке каталогов (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`), а не в вашем `$PATH` — программы из `~/.local/bin`, nvm или conda так не найдутся.
- `ExecReload=` — Команда для мягкой перезагрузки конфигурации без остановки процесса (обычно отправка сигнала SIGHUP).
- `Restart=` — Политика автоматического перезапуска при падении:
  - `no` — не перезапускать никогда.
  - `always` — перезапускать всегда (даже если программа штатно завершилась с кодом 0).
  - `on-failure` — **рекомендуемый выбор**: перезапускать, только если процесс упал с ошибкой, был убит сигналом (OOM Killer) или завершился по таймауту.
- `RestartSec=` — Задержка перед попыткой перезапуска (например, `5s`, `10s`), чтобы при циклическом сбое не перегружать процессор.
- `Environment=` — Переменные окружения, передаваемые в процесс.
- `EnvironmentFile=` — Путь к файлу с переменными (знак минус `-` в начале означает: *«если файл отсутствует, не считать это ошибкой»*).
- `MemoryMax=` / `CPUQuota=` — Ограничения по памяти и процессору. `MemoryMax=` — жёсткий лимит: если сервис его превысит, ядро вызовет OOM Killer только внутри этого сервиса, не затрагивая остальную систему. Мягкий лимит (с замедлением, но без убийства процесса) задаётся параметром `MemoryHigh=`.

#### Разбор параметров секции `[Install]` (Правила включения в автозагрузку)
- `WantedBy=` — Указывает, частью какой цели (Target) становится юнит при включении автозагрузки:
  - Для системных служб: `WantedBy=multi-user.target` (обычный режим работы системы с сетью).
  - Для пользовательских служб: `WantedBy=default.target` (вход пользователя в систему).

> **Что на самом деле делает команда `systemctl enable <имя>`?**  
> Она не запускает службу. Она просто создаёт символическую ссылку (symlink) в каталоге `<target>.wants/`, указывающую на ваш unit-файл. Когда система доходит до этого таргета при загрузке, она видит симлинк и запускает службу.

---

### Типы служб (`Type=`): simple, forking, oneshot, notify

Параметр `Type=` объясняет systemd, как именно программа стартует и в какой момент считать её успешно запустившейся:

1. **`Type=simple` (По умолчанию)**:
   - Подходит для подавляющего большинства современных программ: скриптов Python, приложений Go, Node.js, веб-серверов.
   - Процесс запускается и продолжает работать на переднем плане своего поддерева. systemd считает сервис запущенным сразу после `fork()` — ещё до того, как программа реально стартовала. Поэтому служба с опечаткой в пути сначала «успешно запустится», а потом упадёт. Если важно дождаться реального запуска программы, используйте `Type=exec`.
2. **`Type=forking`**:
   - Используется для классических демонов старой школы (Apache, запускаемый через `apachectl`, Nginx в стандартном режиме и многие старые демоны).
   - Главная программа запускается, создаёт дочерний процесс (fork) и сама немедленно завершается. Дочерний процесс остаётся в памяти как демон.
   - Для таких служб рекомендуется указывать параметр `PIDFile=/run/app.pid`, чтобы systemd точно знал, какой процесс главный (без него systemd пытается угадать сам, и не всегда удачно).
3. **`Type=oneshot`**:
   - Для разовых скриптов, которые должны выполнить действие и сразу завершиться (например, применить правила фаервола, смонтировать специальную папку, обновить сертификат).
   - Следующие службы ждут, пока oneshot-скрипт полностью завершит свою работу.
   - Часто используется совместно с `RemainAfterExit=yes` (чтобы systemd считал службу активной даже после завершения скрипта).
4. **`Type=notify`**:
   - Продвинутый вариант `simple`: программа запускается, инициализирует внутренние компоненты (открывает сокеты, подгружает базу) и в конце шлёт специальный сигнал systemd через сокет (`sd_notify("READY=1")`).
   - systemd не запускает зависимые службы до тех пор, пока этот сигнал не будет получен.

---

### Шпаргалка команд `systemctl`

Все команды имеют одинаковый синтаксис. Для пользовательских служб достаточно добавить флаг `--user` (и не использовать `sudo`). Команды, которые только показывают информацию (`status`, `is-enabled`, `cat`, `list-timers`), работают и без `sudo`.

```bash
# === Управление состоянием ===
sudo systemctl start my-app         # Запустить службу прямо сейчас
sudo systemctl stop my-app          # Остановить службу
sudo systemctl restart my-app       # Перезапустить службу
sudo systemctl reload my-app        # Мягко перечитать конфигурацию (без остановки)
systemctl status my-app             # Посмотреть детальный статус, PID и последние логи

# === Управление автозагрузкой ===
sudo systemctl enable my-app        # Включить автозагрузку при старте
sudo systemctl disable my-app       # Выключить автозагрузку
sudo systemctl enable --now my-app  # Включить автозагрузку И сразу запустить
systemctl is-enabled my-app         # Проверить, включена ли автозагрузка

# === Диагностика и управление конфигурацией ===
sudo systemctl daemon-reload        # Перечитать все unit-файлы с диска (ОБЯЗАТЕЛЬНО после правок!)
systemctl cat my-app                # Показать полный текст unit-файла и всех его override-файлов
sudo systemctl edit my-app          # Открыть редактор для создания override.conf
sudo systemctl edit --full my-app   # Скопировать весь юнит в /etc/ и открыть для полного редактирования
sudo systemctl mask my-app          # Замаскировать службу (запретить запуск вообще кому бы то ни было)
sudo systemctl unmask my-app        # Размаскировать службу
```

> **Для пользовательских служб (без прав root):**
> ```bash
> systemctl --user status my-bot
> systemctl --user restart my-bot
> systemctl --user daemon-reload
> ```

### Чтение логов через `journalctl`

systemd собирает все стандартные потоки вывода (`stdout` и `stderr`) каждого процесса в бинарный журнал `journald`. Вам больше не нужно настраивать отдельные лог-файлы в большинстве случаев.

```bash
# Смотреть логи конкретной системной службы в реальном времени (follow, как tail -f):
journalctl -u my-app -f

# Показать последние 50 строк логов:
journalctl -u my-app -n 50

# Смотреть логи пользовательской службы:
journalctl --user -u my-bot -f

# Показать логи службы только за текущую загрузку компьютера:
journalctl -u my-app -b

# Показать логи за последний час:
journalctl -u my-app --since "1 hour ago"

# Показать только сообщения об ошибках (приоритет err и выше):
journalctl -u my-app -p err
```

### Примеры ситуаций и готовые шаблоны (Systemd)

#### Ситуация 1: Фоновый бот/скрипт пользователя с автозапуском и защитой от падений
*Задача:* У вас есть скрипт Telegram-бота `/home/virusfun/bot/run.py`. Вы хотите, чтобы он стартовал при входе в систему, автоматически перезапускался при ошибках и писал логи в journal. Права root не требуются.

1. Создаём каталог:
   ```bash
   mkdir -p ~/.config/systemd/user
   ```
2. Создаём файл `~/.config/systemd/user/tg-bot.service`:
   ```ini
   [Unit]
   Description=Telegram Notification Bot
   # After=/Wants=network-online.target здесь не помогут: в пользовательском
   # менеджере такой цели нет. От старта без сети страхует Restart=on-failure.

   [Service]
   Type=simple
   WorkingDirectory=/home/virusfun/bot
   ExecStart=/usr/bin/python3 -u run.py
   Restart=on-failure
   RestartSec=5s
   Environment="PYTHONUNBUFFERED=1"

   [Install]
   WantedBy=default.target
   ```
3. Применяем и запускаем:
   ```bash
   systemctl --user daemon-reload
   systemctl --user enable --now tg-bot
   ```
4. Проверяем:
   ```bash
   systemctl --user status tg-bot
   ```

> **Важная фишка для серверов (Linger):**  
> По умолчанию пользовательские службы `--user` запускаются при входе пользователя в систему и завершаются, когда он закрывает последнюю сессию (выходит из графического сеанса или последней SSH-сессии). Чтобы ваши пользовательские службы продолжали работать на сервере всегда (даже когда вы не залогинены), включите режим «задерживания» (linger):  
> `loginctl enable-linger $USER`  
> После этого пользовательский менеджер стартует при загрузке системы, и службы `--user` запускаются без входа пользователя.

---

#### Ситуация 2: Системный веб-сервер Node.js или Go
*Задача:* Развернуть корпоративное веб-приложение на порту 3000 от имени выделенного системного пользователя `appuser`.

1. Создаём файл `/etc/systemd/system/webapp.service` (через `sudo nano`):
   ```ini
   [Unit]
   Description=Production Web Application
   After=network.target

   [Service]
   Type=simple
   User=appuser
   Group=appuser
   WorkingDirectory=/var/www/webapp
   ExecStart=/usr/bin/node server.js
   Restart=always
   RestartSec=3s
   Environment="NODE_ENV=production" "PORT=3000"

   # Ограничиваем аппетит приложения: максимум 1 ГБ ОЗУ
   MemoryMax=1G

   [Install]
   WantedBy=multi-user.target
   ```
2. Активируем:
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable --now webapp
   ```

## 3. Systemd Timers: Современная замена Cron

На системах с systemd вместо cron часто удобнее использовать **таймеры systemd** (сам cron при этом не устарел и по-прежнему широко используется).

### Преимущества перед Cron:
1. **Единые логи:** Вывод запускаемой программы автоматически пишется в журнал службы (`journalctl -u ...`).
2. **Гибкие условия:** Можно запускать задачу не только в фиксированное время, но и «через 15 минут после включения ПК» или «каждые 2 часа после окончания предыдущего запуска».
3. **Защита от пропуска (`Persistent=true`):** Если компьютер был выключен в полночь, когда должен был сработать таймер, при включении утром задача выполнится автоматически! (Работает для расписаний `OnCalendar=`.)

### Принцип парности (`.timer` + `.service`)
Таймер состоит из двух файлов, по умолчанию с одинаковым именем (если имена разные, нужную службу указывают параметром `Unit=` в секции `[Timer]`):
1. `backup.service` — говорит, **что делать** (обычно тип `oneshot`).
2. `backup.timer` — говорит, **когда запускать**.

---

### Анатомия файла `.timer` и синтаксис `OnCalendar`

Файл `~/.config/systemd/user/backup.service`:
```ini
[Unit]
Description=Daily Home Directory Backup

[Service]
Type=oneshot
ExecStart=/home/virusfun/scripts/backup.sh
```

Файл `~/.config/systemd/user/backup.timer`:
```ini
[Unit]
Description=Timer for Daily Backup

[Timer]
# Запускать каждый день в 03:30 утра:
OnCalendar=*-*-* 03:30:00

# Не пропускать запуск, если компьютер был выключен:
Persistent=true

# Небольшой случайный сдвиг запуска до 15 минут (чтобы 100 серверов не атаковали бэкап-сервер одновременно):
RandomizedDelaySec=15m

[Install]
WantedBy=timers.target
```

#### Синтаксис расписания `OnCalendar`
Формат: `ДеньНедели Год-Месяц-Число Часы:Минуты:Секунды`
- `hourly` — каждый час в 00 минут
- `daily` — каждую полночь в 00:00:00
- `weekly` — каждый понедельник в 00:00:00
- `Mon..Fri 09:00:00` — по будням ровно в 9 утра
- `*-*-* *:00/15:00` — каждые 15 минут

---

### Управление таймерами

```bash
# Активировать таймер:
systemctl --user daemon-reload
systemctl --user enable --now backup.timer

# Посмотреть активные таймеры пользователя и когда они сработают в следующий раз
# (неактивные — с флагом --all; системные таймеры — командой systemctl list-timers без --user):
systemctl --user list-timers

# Принудительно запустить службу таймера прямо сейчас для теста (не дожидаясь расписания):
systemctl --user start backup.service
```

## 4. Cron: Классический планировщик задач

Cron — проверенная временем система запуска периодических задач, известная ещё с Unix 1970-х годов. Во многих дистрибутивах она установлена по умолчанию, в некоторых (например, в Arch Linux) её нужно поставить отдельно — пакет `cronie`.

### Где хранятся задания

1. **Пользовательский кронтаб (User crontab):**
   - Физически лежит в `/var/spool/cron/crontabs/<username>` (Debian, Ubuntu) или в `/var/spool/cron/<username>` (Fedora, RHEL, Arch с `cronie`).
   - **Строгое правило:** Никогда не редактируйте этот файл напрямую! Всегда используйте команду:
     ```bash
     crontab -e
     ```
     Команда `crontab -e` проверяет синтаксис перед сохранением и автоматически уведомляет демон `cron` об изменениях.
2. **Системный файл `/etc/crontab`:**
   - Главный общесистемный файл задач. Редактируется через `sudo nano /etc/crontab`.
   - В отличие от пользовательского, содержит **дополнительное поле `user`** (от чьего имени запускать).
3. **Каталог `/etc/cron.d/`:**
   - Сюда программы и пакеты кладут свои конфигурации в формате системного кронтаба (с указанием пользователя).
   - В Debian и Ubuntu файлы здесь должны принадлежать `root`, не должны быть доступны на запись группе и остальным, а имя может состоять только из латинских букв, цифр, `_` и `-`: файлы с точкой в имени (например, `backup.cron`) игнорируются.

---

### Синтаксис 5 и 6 полей cron

```
Пользовательский crontab (5 полей):
 ┌───────────── Минута (0 - 59)
 │ ┌────────────── Час (0 - 23)
 │ │ ┌─────────────── День месяца (1 - 31)
 │ │ │ ┌──────────────── Месяц (1 - 12)
 │ │ │ │ ┌───────────────── День недели (0 - 7, где 0 и 7 = Воскресенье)
 │ │ │ │ │
 * * * * * команда для выполнения
```

```
Системный /etc/crontab (6 полей):
 * * * * * пользователь команда для выполнения
```

#### Спецсимволы:
- `*` — Любое значение (каждую минуту, каждый час).
- `,` — Перечисление (например, `1,15,30` в поле минут = на 1-й, 15-й и 30-й минуте).
- `-` — Диапазон (например, `1-5` в поле дня недели = с понедельника по пятницу).
- `/` — Шаг (например, `*/10` в поле минут = каждые 10 минут).
- `@reboot` — Специальный псевдоним: выполнить один раз при запуске демона cron (то есть при загрузке системы).
- `@hourly`, `@daily`, `@weekly`, `@monthly` — сокращения для распространённых расписаний.
- В полях месяца и дня недели вместо чисел можно писать названия: `jan`…`dec`, `mon`…`sun` (например, `mon-fri`).

---

### 4 главные ловушки новичков в Cron (и как их избежать)

90% проблем вида *«скрипт работает руками, но не работает в cron»* вызваны этими четырьмя причинами:

1. **Минималистичный `$PATH`:**
   - В обычной консоли у вас настроены пути к node, nvm, cargo, conda. В среде cron `$PATH` содержит только `/usr/bin:/bin`.
   - **Решение:** Всегда пишите **абсолютные пути** к интерпретаторам и файлам:
     ```bash
     # НЕПРАВИЛЬНО:
     */10 * * * * python3 script.py
     
     # ПРАВИЛЬНО:
     */10 * * * * /usr/bin/python3 /home/virusfun/scripts/script.py
     ```
2. **Текущая рабочая директория:**
   - Cron запускает команды из домашнего каталога пользователя (`/home/username`), а не из папки, где лежит скрипт. Относительные пути к файлам (`open("data.csv")`) сломаются.
   - **Решение:** Делать переход в папку перед запуском:
     ```bash
     */10 * * * * cd /home/virusfun/scripts && /usr/bin/python3 script.py
     ```
3. **Потеря вывода ошибок:**
   - По умолчанию cron пытается отправить `stdout` и `stderr` локальной почтой (которая обычно не настроена). Если скрипт падает, вы даже не узнаете почему.
   - **Решение:** Всегда перенаправляйте поток вывода и ошибок в лог-файл:
     ```bash
     0 4 * * * /home/virusfun/backup.sh >> /home/virusfun/backup.log 2>&1
     ```
4. **Символ `%` в команде:**
   - В crontab `%` означает перевод строки: всё после первого неэкранированного `%` передаётся команде на стандартный ввод. Поэтому команда с `date +%F` в cron сломается.
   - **Решение:** Экранируйте его обратным слешем:
     ```bash
     0 3 * * * /usr/bin/tar czf /home/virusfun/backup/home-$(date +\%F).tar.gz /home/virusfun/Documents
     ```

## 5. XDG Autostart: Автозапуск приложений рабочего стола

Если вам нужно, чтобы при входе на рабочий стол (KDE Plasma, GNOME, XFCE, Cinnamon) автоматически открывался Telegram, панель виджетов или скриншотер — для этого используется стандарт **XDG Autostart** (FreeDesktop.org).

### Каталоги `.desktop` файлов и их приоритет

Приложения автозапуска описываются файлами с расширением `.desktop`:

1. **Системные (для всех пользователей):**  
   `/etc/xdg/autostart/`
2. **Пользовательские (только для вас, наивысший приоритет):**  
   `~/.config/autostart/`

Если в `~/.config/autostart/` положить файл с таким же именем, как в `/etc/xdg/autostart/`, пользовательский файл полностью перекроет системный.

---

### Формат `.desktop` файла и управление им

Пример файла автозапуска `~/.config/autostart/my-tool.desktop`:
```ini
[Desktop Entry]
Type=Application
Name=Моя Фоновая Утилита
Comment=Автозапуск утилиты при входе на рабочий стол
Exec=/home/virusfun/bin/my-tool --minimized
Icon=utilities-terminal
Terminal=false
Hidden=false
X-GNOME-Autostart-enabled=true
```

#### Ключевые параметры:
- `Exec=` — Команда запуска приложения.
- `Terminal=false` — Не открывать черное окно терминала при старте.
- `Hidden=true` — **Главный способ отключить автозапуск программы!** Если вы хотите отключить назойливое системное приложение из `/etc/xdg/autostart/`, скопируйте его `.desktop` в `~/.config/autostart/` и установите `Hidden=true`.
- `OnlyShowIn=KDE;` / `NotShowIn=GNOME;` — Запускать приложение только в конкретной графической оболочке.

---

### Связь с Systemd Generators (`systemd-xdg-autostart-generator`)

Начиная с systemd 246 автозапуск может выполняться силами systemd. Это используют окружения, которые запускают цель `xdg-desktop-autostart.target`, — например, KDE Plasma (по умолчанию с версии 5.25). Другие окружения (XFCE, MATE и т.п.) запускают `.desktop`-файлы сами, и описанное ниже к ним не относится:

1. При старте вашего пользовательского менеджера systemd (то есть при входе в систему), а также при каждом `systemctl --user daemon-reload` запускается генератор `systemd-xdg-autostart-generator`.
2. Она сканирует папки `/etc/xdg/autostart/` и `~/.config/autostart/`.
3. Для каждого найденного `.desktop` файла она генерирует временный systemd-юнит в оперативной памяти:  
   `/run/user/1000/systemd/generator.late/app-<имя>@autostart.service` (это каталог с самым низким приоритетом).
4. Именно поэтому в `systemctl --user list-units` и в `alirun` вы видите службы вроде `app-org.telegram.desktop...@autostart` или `app-kaccess@autostart`.

> **Как правильно изменять такие службы:**
> - Если вы хотите изменить параметры приложения (флаги запуска, иконку) — редактируйте исходный файл `.desktop` в `~/.config/autostart/`.
> - Если вы хотите настроить для него параметры systemd (ограничение памяти, перезапуск) — создайте drop-in командой `systemctl --user edit app-<имя>@autostart.service`. Не копируйте сгенерированный юнит целиком в `~/.config/systemd/user/`: такая копия перекроет генератор, и последующие правки `.desktop`-файла перестанут применяться.
> - Чтобы отключить автозапуск, используйте `Hidden=true` в `.desktop`-файле (см. выше).

## 6. OpenRC и SysVinit: Для легковесных дистрибутивов без systemd

В минималистичных дистрибутивах (например, **Alpine Linux** на серверах, виртуальных машинах и роутерах, или **Gentoo**) вместо декларативных файлов systemd используются понятные исполняемые шелл-скрипты на базе **OpenRC**.

> В Docker-контейнерах (включая контейнеры на Alpine) init-система обычно не используется вовсе: нужная программа сама работает как PID 1 (иногда через минимальный init — `tini` или `docker run --init`), а перезапуск при падении обеспечивает Docker (`--restart`).

### Философия и уровни запуска (Runlevels)
Вместо таргетов в OpenRC используются уровни запуска (**Runlevels**):
- `sysinit` — самая ранняя инициализация: подключение `/proc`, `/sys`, `/dev`.
- `boot` — монтирование файловых систем, имя хоста, системные часы, загрузка модулей ядра, sysctl.
- `default` — основной рабочий уровень для запуска пользовательских демонов.
- `shutdown` — действия при выключении.

Скрипты служб лежат в каталоге `/etc/init.d/`.

---

### Управление через `rc-service` и `rc-update`

```bash
# Управление состоянием службы:
rc-service nginx start      # Запустить
rc-service nginx stop       # Остановить
rc-service nginx restart    # Перезапустить
rc-service nginx status     # Проверить статус

# Управление автозагрузкой:
rc-update add nginx default # Включить в автозагрузку на уровне default
rc-update del nginx default # Убрать из автозагрузки
rc-update show              # Показать все службы и их уровни запуска
```

---

### Анатомия скрипта OpenRC

Файл `/etc/init.d/my-service` (должен иметь права на выполнение `chmod +x`):
```sh
#!/sbin/openrc-run

name="My Background Daemon"
description="Custom background service for Alpine Linux"

command="/usr/bin/my-daemon"
command_args="--config /etc/my-daemon.conf"
command_background="true"
pidfile="/run/${RC_SVCNAME}.pid"

depend() {
    need net
    after firewall
}
```

- `command=` — путь к исполняемому файлу.
- `command_background="true"` — указывает OpenRC самому отвязать процесс от терминала и отправить в фон, если программа не умеет делать это сама.
- `depend()` — блок зависимостей: `need net` означает, что служба не запустится без рабочей сети.

### SysVinit (Devuan, старые Debian и CentOS)

Классический SysVinit — предшественник systemd и OpenRC. Первым процессом запускается `/sbin/init`, который читает `/etc/inittab` и переводит систему на нужный **уровень запуска**:

| Уровень | Назначение |
| :--- | :--- |
| `0` | Выключение |
| `1` | Однопользовательский режим (восстановление) |
| `2`–`5` | Многопользовательские режимы (в Debian и Devuan они одинаковые; в старых RHEL/CentOS `3` — текстовый, `5` — графический) |
| `6` | Перезагрузка |

Скрипты служб лежат в `/etc/init.d/`, а для каждого уровня есть каталог `/etc/rcN.d/` с символическими ссылками на них: `S20nginx` — запустить (S = start, число задаёт порядок), `K80nginx` — остановить (K = kill).

```bash
# Управление службой (Debian/Devuan):
sudo service nginx start      # также stop, restart, status
sudo /etc/init.d/nginx restart # то же самое напрямую

# Автозагрузка (Debian/Devuan) — создаёт или убирает ссылки в /etc/rcN.d/:
sudo update-rc.d nginx defaults   # включить
sudo update-rc.d nginx disable    # выключить

# Старые RHEL/CentOS 6:
sudo chkconfig nginx on

# Текущий уровень запуска и переход на другой:
runlevel
sudo telinit 3
```

## 7. Сравнительная матрица и алгоритм выбора инструмента

| Задача | Рекомендуемый инструмент | Почему именно он? |
| :--- | :--- | :--- |
| Серверное приложение, бот, API, фоновый рабочий процесс | **Systemd Service** (`.service`) | Автоперезапуск при падениях, контроль памяти, логирование в journald. |
| Периодическая задача бэкапа, очистки диска раз в день/час | **Systemd Timer** (`.timer`) | Защита от пропуска при выключенном ПК, детальные логи работы. |
| Простой периодический скрипт на старом сервере без systemd | **Cron** (`crontab -e`) | Максимальная переносимость, работает на любом Unix/Linux. |
| Окно мессенджера, панель задач или трей при логине на рабочий стол | **XDG Autostart** (`.desktop`) | Стандарт графических окружений KDE/GNOME/XFCE. |
| Служба на системе без systemd (Alpine, Gentoo, Devuan) | **OpenRC** / **SysVinit** (`/etc/init.d/`) | Родная init-система таких дистрибутивов: простые шелл-скрипты, минимум зависимостей. |
| Процесс в Docker-контейнере | **Без init-системы** (`CMD` / `ENTRYPOINT`) | В контейнере программа сама работает как PID 1, перезапуск обеспечивает Docker (`--restart`). |

## 8. Диагностика и решение типовых проблем (Troubleshooting)

### 1. Служба падает сразу после старта (`status: failed` / `exit-code`)
**Как искать причину:**
1. Посмотрите свежие логи с деталями:
   ```bash
   journalctl -u <имя_службы> -n 30 --no-pager
   # для пользовательских служб:
   journalctl --user -u <имя_службы> -n 30 --no-pager
   ```
2. Попробуйте выполнить команду из `ExecStart=` вручную в консоли от имени нужного пользователя:
   ```bash
   sudo -u <пользователь> /путь/к/программе --аргументы
   ```
   Часто сразу становится видно отсутствие нужного файла конфигурации, отсутствие прав доступа или неподгруженную библиотеку.

### 2. Ошибка запуска с кодом 203/EXEC
Код `status=203/EXEC` означает, что systemd **не смог запустить** файл из `ExecStart=`. Причин несколько, а в журнале (особенно в новых версиях systemd) часто видна только сама строка `status=203/EXEC` без пояснений. Проверьте по порядку:
- **Файл существует, и путь написан без опечаток:** `ls -l /путь/к/программе`. Символ `~` в `ExecStart=` не раскрывается — пишите полный путь (в пользовательских службах можно `%h/bin/app`, где `%h` — домашний каталог).
- **Есть право на выполнение:** `chmod +x /путь/к/скрипту`.
- **Шебанг корректен, и интерпретатор установлен:** `head -1 /путь/к/скрипту` должна показать, например, `#!/usr/bin/env python3` или `#!/bin/bash`, и указанный интерпретатор должен существовать.
- **Файл не сохранён с переводами строк Windows:** шебанг вида `#!/bin/bash\r` даёт ошибку «No such file or directory». Проверка: `file /путь/к/скрипту` (покажет `with CRLF line terminators`), исправление: `sed -i 's/\r$//' /путь/к/скрипту`.
- **Раздел не смонтирован с опцией `noexec`** (бывает с `/tmp` и внешними дисками): `findmnt -T /путь/к/программе`.

### 3. Ошибка «Address already in use» (Порт занят)
Служба не может открыться, потому что сетевой порт уже занят другим процессом.
- Проверьте, кто занял порт:
  ```bash
  alirun ports
  # или стандартной системной утилитой:
  sudo ss -tulpn | grep :8080
  ```
- Остановите конфликтующий процесс или смените порт в конфигурационном файле.

### 4. Изменил файл юнита, но настройки не применились
Вы забыли уведомить systemd о том, что файлы на диске изменились (если правили через `systemctl edit`, это делается автоматически):
```bash
sudo systemctl daemon-reload      # для системных
systemctl --user daemon-reload    # для пользовательских
```
